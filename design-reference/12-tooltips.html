Paravent · Prototype

Hover anything underlined

A working tooltip system for every referenceable tag. Mouse hovers, touch taps — the two never share a code path, and the device is judged by what its pointer can do rather than how wide the screen is. Every preview below uses real content pulled from the 5eTools corpus; nothing here is invented.

02 · Every type

One tooltip shape per category

Each category shows only what a gamemaster needs mid-sentence. A creature preview leads with AC and HP; a spell leads with level and range; a condition is just the rule text, because that is the whole question.

03 · Behaviour

The interaction contract

Hover is for mice, touch is for fingers, and the two never share a code path. The device is detected by (hover: hover) and (pointer: fine) — what the input can actually do — not by screen width. An iPad in landscape is 1024px wide and still has no pointer to hover with.

InputBehaviourWhy
hover in mouse onlyOpens after 350 msLong enough to survive a mouse crossing the word on its way elsewhere.
hover out mouse onlyCloses after 180 msGrace period so you can move the pointer into the tooltip to click a button.
hover, already openOpens instantlyOnce you are clearly browsing references, the delay becomes friction.
tap touch onlyOpens a bottom sheetThe only way a tooltip opens on touch. No delay — a tap is already deliberate.
tap again / backdropClosesA finger covers a small popover, so the sheet clears the thumb entirely.
click mouse onlyPins it openSurvives the pointer leaving, so you can click a button inside it.
TabOpens on focusEvery tag is a real <button>. Uses :focus-visible, so a tap does not also trigger it.
EscCloses, returns focusFocus goes back to the tag you came from, never to the top of the page.
dice chipRolls, no previewSame on both: a rollable has nothing to preview.
Never more than one open

Opening a second tooltip closes the first. Reference is a glance, not a workspace — if you want two things side by side, that is what the drawer is for.

Capability, not screen width

Detection is (hover: hover) and (pointer: fine), re-evaluated live — plug in a mouse and hover starts working without a reload. Width would misjudge two real cases: an iPad in landscape (wide, no hover) and a narrow desktop window (small, has hover).

Synthetic mouse events are filtered

Touch browsers replay a fake mouseenter after a tap, which would open the tooltip twice. Listeners are pointerenter/pointerleave and check pointerType === 'mouse', so the replay is ignored.

Nested tags do not chain

A tooltip's own body renders its tags with a dotted underline and no hover target. Chained popovers are unusable with a mouse; "Open full entry" is the way deeper.

It flips rather than clipping

The tooltip measures itself against the viewport and flips above the tag when there is no room below, shifting horizontally to stay on screen. It never renders partly off the edge.

Preview, never the whole entry

A tooltip is capped at roughly six lines. Anything longer belongs in the drawer — a tooltip you have to scroll has failed at being a glance.

04 · Build

How it maps onto FastAPI + HTMX

One endpoint, one fragment

GET /ref/{type}/{slug}/preview returns the tooltip fragment. The renderer emits hx-get with hx-trigger="mouseenter delay:350ms, focus" and hx-target="#tip". No bespoke fetch code.

Cached, because prose repeats

{@creature goblin} appears 54,753 times in the corpus. Preview fragments are pure functions of the compendium — @lru_cache them and invalidate on the JSON watcher's reload signal.

The preview is a different projection

Not a truncated statblock. preview_for(entity) selects per type: creature → AC/HP/speed/CR + abilities; spell → level/school/time/range + one sentence; condition → the rule list, complete.

Degrades without JavaScript

Every tag is a real link to its full entry. Without JS the tooltip never opens and the click navigates to the reference page — the content is always reachable.
